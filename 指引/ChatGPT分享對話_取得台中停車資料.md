# 取得臺中停車資料與停車位預測模型紀錄

## 來源

- 分享對話：[取得台中停車資料](https://chatgpt.com/share/6aebb9eb-fcb8-83ee-81ca-238e540e88ca)
- 對話主題：臺中市免費路邊停車資料蒐集，以及新北市歷史資料建模

## 一、臺中市免費路邊停車資料

### 結論

- 臺中市有免費的即時路邊停車開放資料。
- 對話中未找到可驗證、免費下載且涵蓋多年期間的臺中市路邊剩餘車位歷史資料。
- 若無法向政府或 TDX 取得歷史檔，應定期擷取即時 API，自行累積歷史資料庫。
- 路邊停車格資料與路外停車場資料不可混用；基本位置資料也不能取代帶有觀測時間的占用歷史資料。

### 建議資料來源

| 資料來源 | 用途 | 注意事項 |
|---|---|---|
| [臺中市路邊剩餘車位](https://data.gov.tw/dataset/158166) | 車格即時占用狀態 | 官方標示約每 10 分鐘更新；需實際確認回傳欄位與涵蓋範圍 |
| [TDX 路邊停車路段剩餘位動態資料](https://data.gov.tw/dataset/174353) | 路段層級即時剩餘車位 | 需註冊 API Key，並注意額度或點數規則 |
| [TDX 路邊停車路段基本資料](https://data.gov.tw/dataset/174352) | 路段識別、地圖與靜態特徵 | 不包含歷史占用序列 |
| [臺中市路邊停車格位資訊](https://data.gov.tw/dataset/84296) | 車格位置與 GIS | 不可代替剩餘車位歷史資料 |

對話中記錄的臺中市政府 JSON 資源網址：

```text
https://newdatacenter.taichung.gov.tw/api/v1/no-auth/resource.download?rid=1744bc00-cd16-48f3-9632-309f364662bb
```

使用前應重新驗證網址、授權、更新頻率、JSON 結構及欄位定義。

### 車格狀態與路段統計

對話列出的主要欄位如下：

| 欄位 | 說明 |
|---|---|
| `Section_ID` | 路段編號 |
| `PS_ID` | 停車格編號 |
| `PS_type` | 車格類型 |
| `Lat`, `Lng` | 經緯度 |
| `status = 0` | 空車位 |
| `status = 1` | 已停車 |
| `status = 2` | 偵測器故障 |

路段剩餘位可按 `Section_ID` 彙總 `status = 0` 的筆數。故障狀態應獨立保存，不應直接當成占用或空位。

### 歷史資料取得策略

1. 在 TDX 歷史資料服務搜尋 `CurbSegmentAvailability` 或路邊停車路段剩餘位。
2. 向臺中市政府交通局申請學術研究用途的歷史資料。
3. 若無公開歷史檔，從目前開始每 10 分鐘擷取一次即時資料。

向主管機關申請時，應詢問：

- 是否保存車格占用或路段剩餘位歷史資料。
- 可提供的日期範圍、時間粒度及欄位。
- 是否可提供特定期間或部分路段作學術研究。
- 正式申請程序、授權及使用限制。

## 二、自建歷史資料庫方案

### 建議流程

```text
臺中市即時 API
  → Python 定時擷取
  → 保存原始 JSON
  → 清理及依路段彙總
  → SQLite／PostgreSQL／Parquet
  → 匯出模型訓練資料
```

### 建議保存欄位

- `observed_at`：擷取時間，統一使用 Asia/Taipei。
- `section_id`、`parking_space_id`：路段及車格識別碼。
- `status`：原始車格狀態。
- `total_spaces`、`available_spaces`、`occupied_spaces`、`fault_spaces`：路段彙總。
- `source`、`source_updated_at`：資料來源與來源更新時間。
- 原始回應內容或原始檔路徑，供日後重新清理。

### 執行原則

- 每 10 分鐘排程一次，實際頻率以 API 規範為準。
- 原始資料與清理後資料分開保存。
- API 錯誤、空回應或未知 JSON 結構不可寫成零車位。
- 以唯一鍵避免同一路段、同一觀測時間重複寫入。
- 定期匯出 CSV 或 Parquet，供模型訓練使用。
- 上線前必須以真實回應驗證 JSON 巢狀結構與欄位名稱。

## 三、新北市歷史資料建模紀錄

對話後半段改以使用者購買的新北市路邊停車歷史 JSONL 建立預測模型。

### 資料期間與品質問題

- 資料期間：2025/05/01～2026/11/02。
- 19 個月份 ZIP，共檢查到 425 個 JSONL 日期檔，解壓縮前約 629 MB。
- 2025 年 11 月的壓縮檔未包含 JSONL。
- 部分日期資料量偏少或完全空白。
- 部分月份的 `ParkingSegmentID` 為空白，不能只依此欄位識別路段。
- 路段名稱格式不完全一致，需要標準化及建立對照。

空白日期代表缺少觀測，不可填成剩餘車位 0。路段識別應綜合有效編號、標準化名稱及其他可用位置資訊，無法確認的紀錄需另外標記。

### 20 天資料版本的結果

- 20 個不重複日期檔。
- 1,940,924 筆原始有效紀錄。
- 473,922 筆整理後路段時間紀錄。
- 881 個不同路段編號。
- 以時間順序切分訓練與測試資料，預測每 30 分鐘的剩餘車位。

| 模型 | MAE | RMSE |
|---|---:|---:|
| 歷史時段中位數基準 | 1.94 格 | 3.99 格 |
| HistGradientBoosting | 4.08 格 | 6.43 格 |

此結果顯示，在當時有限的日期覆蓋與特徵設計下，簡單基準模型優於梯度提升模型。數值僅適用於該次測試期間，不能直接代表長期或跨季節預測準確度。

### 完整月份資料版本的交付修正

對話中先提供的完整歷史資料處理 ZIP 只有 `pipeline.py`、`requirements.txt` 與 `README.md`，沒有訓練完成的模型或實際預測結果，屬於不完整交付。

後續補上的已訓練示範版：

- 使用各 JSONL 前 2,500 行做間隔抽樣。
- 共整理 30,112 筆路段時間觀測。
- 測試資料 6,079 筆。
- 模型：HistGradientBoosting。
- MAE：7.12 格。
- RMSE：11.56 格。

此版本只是可執行的抽樣示範版，不是使用 19 個月份全部有效紀錄訓練的正式模型。抽樣方法可能造成時段偏差，測試結果不能代表全量資料的準確度。

## 四、正式模型的驗收條件

正式交付至少應包含：

- 完整資料品質報告：每日筆數、缺漏日期、重複資料、異常值及有效路段。
- 明確的路段識別與名稱標準化規則。
- 依時間順序切分訓練、驗證及測試資料，避免資料洩漏。
- Persistence、歷史平均或歷史時段中位數等基準模型。
- 至少一個機器學習模型及一致的比較方式。
- MAE、RMSE，以及分行政區、平假日、時段的誤差分析。
- 實際模型權重、訓練程式、`predict.py`、套件版本及可重現的執行說明。
- 清楚標示實際使用的資料期間、筆數與抽樣方式。
- 可直接執行的預測範例與輸出檔，不得把空專案描述為已訓練模型。

## 五、專題應採用的做法

1. 臺中市部分先驗證即時 API，建立定時擷取與歷史資料庫。
2. 同步向 TDX 與臺中市政府申請免費歷史資料。
3. 新北市資料先完成完整品質檢查及路段識別修正，再進行全量訓練。
4. 先建立簡單基準模型，再比較較複雜模型是否真的改善預測。
5. 報告中必須區分原型、抽樣示範版與全量正式模型，並如實揭露限制。
