期末專題提案作業規範
Final Project Proposal Requirements
一、作業目的與基本要求

本期末專題旨在訓練學生完成一個從問題發現、資料蒐集、領域研究、AI 分析、系統設計，到實作與驗證的完整專案。專題應以真實世界問題為核心，原則上採用：

AI Agent + Domain Knowledge + Data Analytics + Real-World Application

學生不應只訓練一個 AI Model 或製作單純 Chatbot，而應設計一個具有特定專業能力的 Domain AI Agent（領域智慧代理人），能夠理解使用者需求、取得與分析資料、結合領域知識進行推理，最後提供有依據的結果、預測、診斷或建議。

例如：AI Plant Doctor、Energy Detective、Warehouse Manager、Factory Doctor、Financial Analyst、Architect Assistant、Pet Life Analyst 等。

二、Final Project Proposal（10%）

Proposal 為期末專題第一階段，占成績 10%，須完成以下四部分：

1. Abstract 摘要

摘要應形成完整的研究故事，建議採用以下 A–F 六段式結構：

A. Attention Getter — Motivation
以具體證據說明「為什麼這個問題現在很重要、創新或有趣」。應優先尋找 2025–2026 的研究論文、政府/產業報告、統計資料、公開資料集、科技新聞或真實案例，不應只寫「近年來 AI 快速發展」。

B. But — Challenge
指出現有技術、應用或研究仍存在的問題、限制與 Research Gap。

C. Cure — Proposed Solution
清楚說明：「為了解決上述問題，本專題提出一個新的 ______ AI Agent / System。」

D. Development — Method
簡述系統如何整合 AI、資料來源、分析方法及 Domain Knowledge。

E. Experiments — Evaluation
說明預計使用的 Dataset、Case Study、Baseline、Evaluation Metrics 或使用者測試。

F. Findings — Expected Outcomes
Proposal 尚未完成實驗者應寫 Expected Findings / Expected Outcomes，不得虛構實驗結果。

Abstract Story：Attention Getter → But → Cure → Development → Experiments → Findings

2. Introduction 緒論

Introduction 必須回答：Why is this project worth doing?

建議使用 A–F 結構：

**A. Attention Getter：**以公開數據、研究、報告或案例引題。
**B. Background：**說明應用領域、使用者及技術背景。
**C. Problem：**明確定義真正需要解決的問題。
**D. Existing Limitations：**說明目前方法的不足與挑戰。
**E. Innovation：**說明你的方法與既有系統有何不同。
**F. Contributions：**條列本專題預期的主要技術與應用貢獻。

Introduction 中的重要論述應盡可能有客觀證據與來源支持。

3. Related Work 相關研究

Related Work 應同時涵蓋：

約 1/2 AI Technology + 1/2 Domain Know-how

例如「AI Plant Doctor」不能只研究 CNN、Transformer、LLM，也必須研究植物病害、環境因子、土壤濕度、農業感測器及相關農業資料。

可使用 Perplexity、Connected Papers、NotebookLM、Google Scholar、GitHub、Udemy 等工具協助研究，但學生必須確認原始來源及內容正確性。

最後必須歸納：

Existing Research → Limitations → Research Gap → Our Project

四、Proposed Scheme / Proposed Design

Proposed Scheme 是本 Proposal 最重要的技術內容，必須將專題設計成可實作的 AI Agent System。

基本架構可參考：

① User/Application Scenario

→ ③ Planner & Reasoning Agent
→ ④ Data Acquisition/Retrieval
→ ⑤ Analytics Engine
→ ⑥ Domain Knowledge Integration
→ ⑦ Decision/Recommendation
→ ⑧ Output & Interaction

資料來源可以包含 IoT Sensor、Database、CSV/Excel、API、Web、Open Data、PDF/Paper、Knowledge Base、Vector DB 等。

Proposal 必須提供以下三種技術表示

1. System Architecture
必須有完整架構圖，各主要模組以 ①②③… 編號，並在正文逐一說明。

2. Flowchart
呈現 Input → Processing → AI/Analytics → Decision → Output 的完整處理流程；必要時加入 Decision、Loop、Exception 或 Human Interaction。

3. Pseudocode
核心演算法必須提供具有行號的 Pseudocode，例如：

Algorithm 1: Domain AI Agent

Output: Domain-specific Result R

01: Receive user query Q
02: Analyze intent and requirements
03: Decompose Q into subtasks

06: Analyze data using AI/ML methods
07: Integrate results with domain knowledge
08: Generate candidate solutions
09: Evaluate evidence, uncertainty, and limitations
10: Generate final recommendation R
11: Present results and supporting evidence

本專題允許並鼓勵合理使用 AI。可使用 ChatGPT、Claude、Gemini、NotebookLM、Perplexity、Connected Papers、GitHub Copilot、Codex 等工具進行：

Research、Literature Review、Coding、Debugging、Architecture、Data Analysis、Pseudocode、Documentation、PPT 等工作。

AI 可以幫你完成工作，但你必須能解釋它做了什麼、為什麼這樣設計，以及如何驗證結果。

二、我建議的專題定位

我會把研究範圍定在臺中市公有路外停車場的剩餘車位預測，先不把所有路邊停車格都納入第一版。

原因是路外停車場通常有明確的總車位數，可以將剩餘車位數轉換成占用率，較容易建立預測標籤與比較不同停車場的使用情況。

建議研究題目

基於多源資料分析與領域知識推理之智慧停車 AI Agent：以臺中市剩餘車位預測為例

英文：A Smart Parking AI Agent Based on Multi-source Data Analytics and Domain Knowledge Reasoning: A Case Study of Parking Availability Prediction in Taichung City

核心研究問題

1. 能否利用歷史車位變化與時間特徵，準確預測未來 30／60 分鐘的剩餘車位？
2. 加入天氣、星期、假日等外部特徵，是否能改善預測表現？
3. AI Agent 能否將預測結果、停車費率、距離與滿位風險整合成有依據的推薦？

這個定位同時包含了 AI、資料分析、領域知識與應用系統，也保留了可以透過實驗驗證的研究問題。

三、系統應該怎麼設計？

我建議將系統拆成八個模組，這樣可以直接對應老師要求的 System Architecture、Flowchart 與 Pseudocode。

① User Interface & GIS Map

輸入目的地、預計抵達時間、停車偏好

② Planner & Reasoning Agent

理解需求、拆解任務、選擇資料與分析工具

③ Data Acquisition

政府 API、歷史資料、天氣、停車費率

④ Data Processing

清理缺失值、時間對齊、特徵工程

⑤ AI Analytics & Prediction Engine

預測未來車位數、占用率及滿位機率

⑥ Domain Knowledge & Decision Engine

結合容量、費率、距離、滿位風險與使用者偏好

⑦ Recommendation & Explanation Agent

排序停車場、說明推薦理由、呈現預測信心

⑧ Results Dashboard

地圖、預測曲線、推薦清單、資料時間與風險提示

這裡最重要的區分是：AI 預測模型負責估算未來車位；Agent 負責決定要查什麼資料、使用哪種分析工具，以及如何依據使用者需求提出建議。 不需要把所有功能都交給大型語言模型。

四、AI 模型要用什麼？

建議先以容易解釋、容易比較的模型開始，再視資料量決定是否使用深度學習。

模型  用途  在專題中的角色
Historical Average  同星期、同時段的平均車位  基準模型
Linear Regression  預測未來剩餘車位數  可解釋的基準模型
Random Forest  學習時間、歷史車位與外部因素的非線性關係  主要候選模型
XGBoost  分析多種特徵與複雜交互作用  主要候選模型
LSTM  學習較長的時間序列變化  資料充足時再評估

2025 年一篇停車占用率研究使用可解釋的統計模型分析停車行為，也指出簡單模型在特定規律場景中具有實用價值。另一篇多源資料研究則比較了 LSTM、Transformer 等模型。這表示你不必預設深度學習一定最好，而應透過實驗選擇合適的方法。

建議預測的目標

主要目標：

- 未來 30 分鐘剩餘車位數。
- 未來 60 分鐘剩餘車位數。
- 未來 30／60 分鐘達到滿位狀態的機率。

評估方式：

- MAE、RMSE：預測車位數與實際車位數相差多少。
- Precision、Recall、F1-score：判斷是否能正確預警滿位風險。
- Baseline comparison：確認 AI 是否真的優於歷史平均等簡單方法。

訓練與測試資料應依時間切分，不能把未來資料洩漏到訓練階段。

關鍵設計決策

- 資料過期： 不可直接把舊資料當作目前狀態；依更新時間與預先定義的有效期限判斷。
- 感測器故障： 路邊車格狀態為故障時，不計入確定的空位數。
- 模型不可用： 可以回傳即時資料及簡單基準估計，但必須標示為基準估計，而不是正式模型預測。
- 候選皆不符合： 回報原因，請使用者調整預算、步行距離或抵達時間。
- 結果可驗證： 保存預測當下的資料版本、預測值、模型版本及目標時間，供事後比較。

這裡的第 23 行可以先使用明確的加權評分規則，而不是讓 LLM 自行決定分數。例如將距離、預估費用、可用車位及滿位風險標準化後，再依使用者偏好設定權重。

不過，「可用車位多」不一定等於「最適合使用者」。對預算敏感的使用者，費率權重應較高；對時間敏感的使用者，距離與滿位風險可能更重要。這就是 Domain Knowledge 與 Agent 決策的價值。

七、Domain Knowledge：專題不能只靠模型

老師特別要求領域知識，因此建議你在系統中明確定義以下規則。

領域知識  規則或意義  對系統的影響
停車容量  剩餘車位不能小於 0，也不能大於總容量  預測值需合理化
車格狀態  故障、未知與空位是不同狀態  避免高估空位
時間週期  平日、假日、尖峰與離峰需求可能不同  建立時間特徵
空間關係  鄰近路段與停車場可能存在共同需求  加入空間特徵
收費制度  每小時費率、計費單位及上限影響實際成本  估算預計停車費
資料不確定性  即時資訊與預測都可能有誤差  顯示信心與資料時間

需要注意：這些是待驗證的領域假設，不應直接當成臺中市所有停車場都成立的事實。例如尖峰時段是否固定、附近停車場之間是否存在替代關係，都應透過資料分析驗證。

8.2 Evaluation Metrics

車位數預測：MAE、RMSE

$$\operatorname{MAE}=\frac{1}{n}\sum_{i=1}^{n}|y_i-\hat y_i|$$

MAE 可直接解讀為平均預測誤差幾個車位；RMSE 則對較大的預測錯誤給予較高懲罰。

滿位風險分類：Precision、Recall、F1-score

衡量系統是否能正確識別接近滿位或已滿位的情況。滿位門檻應事先定義，並依資料特性調整。

推薦品質：Top-k 命中率與成本比較

比較推薦清單中實際有空位的比例、預估費用與距離。若沒有可靠的實際抵達時間或使用者行為資料，應先將這些視為離線模擬指標，而不是宣稱已降低實際尋位時間。

8.3 必須避免的實驗錯誤

1. 依時間切分訓練、驗證與測試資料。
2. 不得使用預測時間之後才知道的資料作為輸入特徵。
3. 不應將感測器故障誤當成空位或占用。
4. 路外停車場與路邊車格應分別評估，再評估整合系統。
5. 模型的所有預測結果都要與實際觀測值比較，不能只展示看起來合理的案例。
